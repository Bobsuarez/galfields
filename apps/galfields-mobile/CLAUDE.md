## Architecture

This is an **Expo 54 / React Native 0.81** app using **file-based routing via expo-router 6**. The New Architecture (`newArchEnabled: true`) and React Compiler (`experiments.reactCompiler: true`) are both enabled.

### Routing

Routes live under `app/`. expo-router turns filenames into URL segments automatically:

- `app/_layout.tsx` — root Stack navigator; wraps everything in `ThemeProvider` (light/dark)
- `app/(tabs)/_layout.tsx` — bottom tab navigator (Home, Explore)
- `app/(tabs)/index.tsx` — Home tab
- `app/(tabs)/explore.tsx` — Explore tab
- `app/modal.tsx` — modal screen (opened via `router.push('/modal')`)

The `unstable_settings.anchor = '(tabs)'` in the root layout makes the tabs group the default deep-link anchor.

Beyond the tabs, top-level auth-gated route groups are registered in `app/_layout.tsx`'s Stack: `login`, `products`, `settings`, `reports`, `inventory`. Each follows the same shape — a `<Name>Layout` in `app/<name>/_layout.tsx` that redirects to `/login` when `!isAuthenticated` (see `contexts/auth-context.tsx`), a thin per-screen route file that just renders a component from `components/<name>/`, and a hub screen (`index.tsx`) listing sub-screens as cards (see `app/settings/index.tsx` or `app/reports/index.tsx`) — except `inventory`, which is a single screen, not a hub. `services/<name>-api.ts` holds the fetch calls for that feature (`apiBaseUrl()` + `parseApiErrorMessage`, see `services/api-base-url.ts`/`services/api-error.ts`) — copy an existing one (`services/reports-api.ts` is the most recent) rather than inventing a new API-client shape.

**The backend URL is a runtime setting, not a build-time env var** — `services/api-base-url.ts` used to just read `EXPO_PUBLIC_API_BASE_URL` directly (baked into the JS bundle at build time, unchangeable without rebuilding). Now it's backed by `@react-native-async-storage/async-storage`, editable from Configuración → Servidor (`app/settings/server.tsx`, `components/settings/server-screen.tsx`) — same intent as the desktop POS's Configuración → Reglas y Sincronización "URL del servidor" field (see `apps/galfield-pos`'s CLAUDE.md), so either app can point at a different backend without a rebuild. `apiBaseUrl()` itself **stays synchronous** (every `services/*-api.ts` file calls it inline inside a template literal), backed by an in-memory cache populated once by `initApiBaseUrl()` — `app/_layout.tsx` calls that at boot, behind an `expo-splash-screen` gate (`SplashScreen.preventAutoHideAsync()`/`hideAsync()`), and renders nothing until it resolves, since `ProductsProvider` (wrapping the whole app) fetches immediately on mount and would throw if `apiBaseUrl()` were called before the cache is populated. `setApiBaseUrl(url)` validates (`http://`/`https://` prefix), persists, and updates the cache in one call — no restart needed for a change to take effect. `resetApiBaseUrl()` clears the override, reverting to `EXPO_PUBLIC_API_BASE_URL`. **Don't add a new `apiBaseUrl()` call site that awaits anything** — the synchronous contract is what every existing `services/*-api.ts` file relies on.

**Login is real now, not the old `admin`/`1234` demo** (spec `01-login-empleados-roles`, step 8 of 17 — steps 10-12 of that same spec, still pending, add Roles/Empleados management screens and a shared `Authorization: Bearer` attach-point here). `services/auth-api.ts`'s `login()` hits `POST /api/auth/login` with no `terminalCode` (that field is desktop-only — see `backend/pos`'s CLAUDE.md, "Employee login / JWT") — the backend itself rejects (401) any employee whose role has `can_login_mobile=false` (e.g. a `Cajero`), so `contexts/auth-context.tsx` doesn't need its own role check on top. `AuthProvider`'s `login()` persists the JWT (`AsyncStorage` key `auth.jwt`) and the mapped `User` (`role: response.roleName`, key `auth.employee`) together, same two-key pattern the spec's "Mobile — sesión" section describes. **No client-side expiry check** — the JWT's own `exp` is the only expiration; a call that comes back 401 is meant to force a logout + redirect to `/login` (step 12, not yet wired — nothing currently reads `AuthContext`'s `token` to attach it to a request or react to a 401 yet, so today's screens don't call authenticated backend endpoints at all).

`restoreAuthSession()` (same file) is loaded once at boot in the same `Promise.all` as `initApiBaseUrl()`/`initImageSearchProvider()` (`app/_layout.tsx`), and its result is passed into `<AuthProvider initialSession={...}>` — **not** a module-level sync cache like `apiBaseUrl()`, since `user`/`token` are real React state consumed only through `useAuth()`, never read outside a component. This is what makes a session survive an app reload without ever flashing `/login`: every auth-gated `_layout.tsx` (see above) reads `isAuthenticated` synchronously on first render, so if the restore happened after that first render instead of before it, a logged-in user would briefly bounce to the login screen on every cold start.

**Configuración → Terminales** (`app/settings/terminals.tsx`, `components/settings/terminals-screen.tsx`, `services/terminals-api.ts`, spec `01-login-empleados-roles` step 9) manages `backend/pos`'s `terminals` table (see that repo's CLAUDE.md, "Terminals CRUD") — `terminalCode`, an optional display `name`, and `active`. **Not** built on the shared `CatalogScreen`/`CatalogFormModal` (unlike categories/brands/locations/invoicing) — same reason `payment-methods` isn't either: `active` needs a real toggle, and `CatalogFormModal` only renders plain text fields (`Record<string, string>` values, no boolean/switch field type). `terminals-screen.tsx`/`terminal-form-modal.tsx` instead mirror `payment-methods-screen.tsx`/`payment-method-form-modal.tsx`'s bespoke shape (still built on the shared `useCatalogCrud` hook, which *is* generic enough for this — only the list/form UI needed to be bespoke, not the CRUD state machine).

**This is also what unbroke Numeración de facturas** (`app/settings/invoicing.tsx`): `backend/pos`'s `InvoiceNumberingRangeRequest` swapped `terminalCode` (loose string) for `terminalId` (FK to the now-real `terminals` table) as part of the same backend migration that added the table above — until this step, `invoicing.tsx` was silently sending a request shape the backend no longer accepted. The screen still shows the same "Código de terminal" text field as before (no picker UI) — `invoicing.tsx` now also loads the terminals list on mount and resolves the typed code to a `terminalId` inside `fromFormValues`, throwing a plain `Error` (caught by `CatalogScreen`'s existing try/catch → `Alert.alert`, no new error-handling plumbing needed) if the typed code doesn't match any known terminal. A range can now only be assigned to a terminal that already exists in Configuración → Terminales — create it there first.

**Configuración → Roles** (`app/settings/roles.tsx`, `components/settings/employee-roles-screen.tsx`, `services/employee-roles-api.ts`, spec `01-login-empleados-roles` step 10) manages `backend/pos`'s `employee_roles` (see that repo's CLAUDE.md, "Employee roles CRUD"). Same bespoke-screen reasoning as Terminales above — `roleName` plus 6 independent booleans (4 module permissions + `canLoginMobile`/`canLoginDesktop`) don't fit `CatalogFormModal`'s plain-text fields either. Toggles use React Native's own `Switch` (`trackColor={{ true: Brand.orange }}`, same convention as `components/inventory/inventory-screen.tsx`'s "Mostrar desactivados" switch), not a bespoke checkbox — one row per boolean, grouped into "Permisos por módulo" and "Acceso". `services/employee-roles-api.ts`'s `PERMISSION_MODULES` hardcodes exactly the 4 module keys the spec's mobile grid asks for (`pos`, `inventario`, `reportes`, `sync`) — the backend's `permissions` map itself isn't restricted to these (a future module can be added there without a backend change, see backend/pos's CLAUDE.md). `employee-role-form-modal.tsx` seeds its local state as `{ ...emptyPermissions(), ...editing.permissions }`, so any key outside `PERMISSION_MODULES` that's already on a role (from some future caller) round-trips through an edit untouched instead of silently getting dropped — this UI just never introduces one itself.

**Configuración → Empleados** (`app/settings/employees.tsx`, `components/settings/employees-screen.tsx`, `services/employees-api.ts`, spec `01-login-empleados-roles` step 11) manages `backend/pos`'s `employees` (see that repo's CLAUDE.md, "Employees CRUD") — the most complex of these four bespoke-CRUD screens, since it needs two pickers (single-select role, multi-select terminals), not just toggles. `employees-screen.tsx` fetches the roles and terminals lists itself (`employeeRolesApi.list()`/`terminalsApi.list()`, once on mount) and passes them into `employee-form-modal.tsx` as plain props — the modal stays a controlled component like every other form modal here, it doesn't fetch its own data. Both pickers are Pressable "chip" rows (`chipSelected` = `Brand.orange` background/border) rather than a native picker/dropdown — role is single-select (tapping one deselects the rest), terminals is a toggle-each multi-select (`terminalIds: number[]`).

- **Password is required only on create.** On edit, leaving the password field blank sends `password: undefined` — `EmployeeFormData.password` is optional specifically so `employeesApi.update` can omit it, matching the backend's "blank/missing on `PUT` leaves `password_hash` untouched" contract exactly (this is the spec's deliberate password-reset mechanism: an admin resets a forgotten password by editing the employee and setting a *new* one, there's no separate reset flow).
- **`DELETE` here means deactivate, not delete** — same backend semantics as `/api/products`, see backend/pos's CLAUDE.md. The confirmation dialog says "Desactivar"/"Ya no podrá iniciar sesión" (not "Eliminar"/"no se puede deshacer", which `employees-screen.tsx` deliberately avoids — unlike the other three screens' `confirmDelete`, this one really is reversible on the backend, just not from any UI that exists yet). `useCatalogCrud`'s `remove` still just filters the item out of the local list, same as everywhere else — a deactivated employee simply drops off this screen, there's no "show deactivated" toggle or reactivate button (the backend doesn't have a reactivate endpoint yet either).

**Every authenticated backend call now attaches `Authorization: Bearer <jwt>`, and a global 401 forces a clean logout** (spec `01-login-empleados-roles` step 12 — the last mobile step, though the JWT itself has existed since step 8). Two new files split this into a non-React, purely-synchronous half and a React half, same reasoning as `api-base-url.ts`'s cache-vs-hook split:

- **`services/auth-token.ts`** — a module-level `cachedToken`, mirroring `api-base-url.ts`'s pattern exactly (`services/*-api.ts` files build fetch calls synchronously and can't call `useAuth()`), plus a single-slot `onUnauthorized`/`notifyUnauthorized` pair — a plain pub/sub of one listener, not an event emitter library, since there's only ever one thing that needs to react to a 401 (the logout).
- **`services/authenticated-fetch.ts`** — `authenticatedFetch(url, init)`, a drop-in replacement for `fetch()` that adds the header (if a token is cached) and calls `notifyUnauthorized()` on any 401 **before** returning the response to the caller, so the global logout fires regardless of how that specific caller then handles the non-ok response.
- **Every `services/*-api.ts` file's `fetch(` call site was swapped to `authenticatedFetch(`**, except two deliberate holdouts: `auth-api.ts`'s `login()` (a 401 there means "wrong password", not "session expired" — routing it through the same handler would force-logout a user who was never logged in, right as they're trying to log in) and `image-search.ts` (calls Google/SerpApi directly — attaching our backend's Bearer token to a *third-party* request would leak it).
- **`contexts/auth-context.tsx`'s `AuthProvider`** wires the two together: one `useEffect(() => setAuthToken(token), [token])` keeps the module cache in sync with React state (covers login, logout, *and* the restored-session case on boot, since it also runs on mount); another registers `onUnauthorized(() => { logout(); router.replace('/login'); })` once, on mount.
- **Known rough edge, not fully polished:** a screen whose own `try/catch`/`useCatalogCrud` error state was already showing an `Alert.alert` for that same failed call may still flash it briefly alongside the redirect — the global handler forces the logout+redirect regardless, but doesn't suppress each individual call site's own error UI. `parseApiErrorMessage` still extracts the backend's clean JSON message either way (never a raw stack trace/crash), so this is a UX nicety left for later, not a "raw error" in the sense the spec's acceptance criterion cares about.

`app/reports/` is a read-only dashboard over `backend/pos`'s `GET /api/reports/*` endpoints (see that repo's CLAUDE.md for exactly what each one returns) — sales summary, cash summary, sales by payment method, current inventory, low stock, and invoice history/detail. It depends on the desktop POS (`apps/galfield-pos`) actually reporting sales to the cloud via `POST /api/sales` — before that existed, these screens have nothing real to show.

**Historial de facturas shows the real DIAN invoice number, not the cloud transactionId** — `services/reports-api.ts`'s `formatInvoiceNumber` reads `invoiceNumber` (the prefix+consecutive string snapshotted by the desktop terminal at sale creation, e.g. `"FAC-000501"` — see `backend/pos`'s CLAUDE.md, "invoicePrefix/invoiceNumber", and `apps/galfield-pos`'s `invoices.rs::create_sale`) and falls back to `#{transactionId}` only when it's `null` — which is only true for invoices reported before the cloud tracked this field. Both `invoice-list-item.tsx` and `invoice-detail-screen.tsx` (header title + cancel confirmation) go through this one helper — don't reintroduce a raw `#{transactionId}` display at a new call site, or it silently regresses back to showing the internal id instead of the number that was actually printed on the ticket.

`app/inventory/` (`components/inventory/inventory-screen.tsx`) is the **read/write** counterpart to `reports/inventory.tsx`'s read-only view — one row per product **variant** (not per product, since each variant has its own stock/barcode; `InventoryScreen`'s local `flattenProduct` mirrors the same "Camiseta Basica - Rojo M" naming convention `apps/galfield-pos`'s `sync.rs` uses), backed by `GET /api/products?includeInactive=true` (`services/products-api.ts`'s `fetchProducts`, extended with an `includeInactive` param — the regular Products catalog screen never passes it, since a deactivated product shouldn't be offered for sale there). A "Mostrar desactivados" switch toggles that flag and triggers a fresh page-0 load. Two write actions per row:
- **Stock**: tapping the stock number opens `StockEditModal`, which asks for the *new total count* (not a +/- delta) — the modal computes `delta = newStock - currentStock` and `services/inventory-api.ts`'s `adjustVariantStock` reports just that delta to `POST /api/inventory/adjustments` (see `backend/pos`'s CLAUDE.md), generating a fresh client-side UUID (`utils/uuid.ts`'s `generateUuid` — a plain `Math.random()`-based v4, not `expo-crypto`, to avoid a new dependency) as that endpoint's required `clientEventId` per call.
- **Activate/deactivate**: the row's toggle icon calls `services/products-api.ts`'s `deactivateProduct`/`activateProduct` (`DELETE`/`PUT .../activate` on `/api/products/{id}` — see `backend/pos`'s CLAUDE.md's "Activate/deactivate" section), confirmed via `Alert.alert` first. Both act on the whole **product** (all its variants together), matching the backend's cascade — there's no independent per-variant toggle.

**Unidades de venta** (`app/products/[id]/units/[variantId].tsx`, `components/products/product-units-screen.tsx`, `services/product-units-api.ts`, spec `03-unidades-venta-conversion` step 4) manages `backend/pos`'s `product_units` (see that repo's CLAUDE.md, "Sale units with conversion factors" / "CRUD .../units") — per-**variant** sale presentations sharing the same physical stock (e.g. "Media"/"Completa" cajetilla of the same SKU), each with its own name/factor/price/barcode.

- **Reached from a variant's card inside `app/products/[id]/edit.tsx`**, not from a top-level Configuración hub like Terminales/Roles — a "Unidades de venta" button (dashed outline, same visual treatment as "Agregar variante") appears inside `VariantFormCard` **only for a variant that already exists on the backend** (`ProductVariantDraft.variantId` set by `toVariantDraft` in `services/products-api.ts`) — a newly-added, unsaved variant draft has no real `variantId` yet, so the button is simply omitted (`onManageUnits` prop left `undefined`) until that variant is saved once. Route: `/products/[id]/units/[variantId]`, registered in `app/products/_layout.tsx` alongside `[id]/edit`.
- **Not built on the shared `CatalogFormModal`** — same reasoning as Terminales/Roles/Empleados: `conversionFactor`/`unitPrice` are numeric fields needing `keyboardType="numeric"`, which `CatalogFormModal`'s plain-text fields don't support. `product-units-screen.tsx`/`product-unit-form-modal.tsx`/`product-unit-list-item.tsx` mirror `terminals-screen.tsx`'s bespoke shape instead, still on the shared `useCatalogCrud` hook.
- **`services/product-units-api.ts`'s `productUnitsApi(productId, variantId)` is a factory, not a fixed object** like every other `*-api.ts` — sale units have no standalone list endpoint (they're only ever read nested under a variant inside `GET /api/products/{productId}`, see backend/pos's CLAUDE.md), so `list()` calls `fetchProduct(productId)` and picks out this one variant's `units[]`; `create`/`update`/`remove` close over `variantId` to hit the real `/api/product-variants/{variantId}/units` endpoints directly. The screen builds this factory once per `(productId, variantId)` pair via `useMemo`, so `useCatalogCrud`'s load effect (keyed on the `api` object reference) doesn't refetch on every render.
- **The base unit (`isBase: true`) can't be deactivated or have its factor changed** — mirrors the backend's own validation (a 409/400 if attempted): `ProductUnitListItem` hides the deactivate action entirely for the base unit rather than letting the user hit that error, and `ProductUnitFormModal` locks the "Factor de conversión" field (read-only, with an explanatory hint) whenever `editing.isBase` is true.
- **`DELETE` here means deactivate, not delete** (soft, `is_active=false` on the backend) — the confirmation dialog says "Desactivar"/"Ya no se podrá vender... hasta reactivarla" (not "Eliminar"/"no se puede deshacer"), same wording precedent as Empleados' `confirmDelete`, for the same reason: it's genuinely reversible on the backend (there's no reactivate button here either yet, matching Empleados — the deactivated unit just drops off the list).
- **Known gap, inherited from the backend (not fixed here):** a variant created after `V10__product_units.sql`/before this screen existed has no base unit at all, and creating one through this screen's `POST` never creates a base (`ProductUnitService#createUnit` hardcodes `isBase=false` on the backend) — so a variant with zero units shows the empty state ("Esta variante todavía no tiene unidades de venta configuradas") with no way to establish a base unit from here. Out of scope until the backend gains a way to do that.

### Theming

- `constants/theme.ts` — `Colors` (light/dark palettes) and `Fonts` (platform-specific font stacks)
- `hooks/use-color-scheme.ts` — re-exports `useColorScheme` from `react-native`
- `hooks/use-color-scheme.web.ts` — platform override for web
- `hooks/use-theme-color.ts` — resolves a named color key from `Colors` for the current scheme; accepts per-prop overrides

Themed components (`ThemedText`, `ThemedView`) use `useThemeColor` internally.

### Platform-specific files

Use React Native's platform extension convention for platform splits:
- `.ios.tsx` — iOS-only implementation (e.g., `icon-symbol.ios.tsx` uses native SF Symbols)
- `.web.ts` — web-only implementation (e.g., `use-color-scheme.web.ts`)
- No suffix — Android and web fallback

`IconSymbol` maps SF Symbol names (iOS) to Material Icons (Android/web). Add new icon mappings in the `MAPPING` object inside `components/ui/icon-symbol.tsx`.

### Path alias

`@/` resolves to the repo root (configured in `tsconfig.json`). Use `@/components/...`, `@/hooks/...`, `@/constants/...` for all internal imports.
